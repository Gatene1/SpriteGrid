SG4GSS
SpriteGrid Sprite Sheet File Specification v4.0 (Updated)

----------------------------------------
FILE OVERVIEW
----------------------------------------
A .gss file is a custom SpriteGrid sprite sheet container.

It consists of:
1. A magic header
2. A JSON file-level metadata section
3. A structured data-dump payload
   - SPRITES
   - PLACEMENTS
   - META (per-sprite metadata)

This format is intentionally:
- Human-readable
- Versioned
- Hand-designed (not generic JSON)

----------------------------------------
FILE STRUCTURE (HIGH LEVEL)
----------------------------------------
SG4GSS
{ FILE METADATA (JSON) }
---
SPRITES
P-records...
PLACEMENTS
L-records...
META
M-records...

----------------------------------------
1. MAGIC HEADER
----------------------------------------
SG4GSS

Identifies the file as a SpriteGrid v4 sprite sheet.
Must appear on line 1.
Parser should reject files without this header.

----------------------------------------
2. FILE METADATA SECTION (JSON)
----------------------------------------
Purpose:
- Describe how to interpret the sprite sheet
- Store file-level information
- Does NOT contain pixel data
- Does NOT contain per-sprite metadata

Example:

{
  "type": "spritesheet",
  "name": "Untitled Sheet",
  "createdUtc": 1736559000000,
  "modifiedUtc": 1736560123000,
  "notes": null,
  "gridCellSize": 16,
  "colorParadigm": "ABGR",
  "spriteCount": 12
}

Metadata ends at the first line containing only:
---

----------------------------------------
3. PAYLOAD SECTION
----------------------------------------
Everything after --- is the data dump.
Order of sections is fixed.

----------------------------------------
3.1 SPRITES SECTION
----------------------------------------
Begins with:
SPRITES

Each sprite is defined by a P-record.

P-RECORD FORMAT:
P:<id>:<wPx>:<hPx>:<createdUtc>:<modifiedUtc>:<pixelData>

Field Definitions:
- id            Unique sprite ID
- wPx           Width in pixels
- hPx           Height in pixels
- createdUtc    Creation timestamp
- modifiedUtc   Last modification timestamp
- pixelData     Comma-separated Uint32 values (ABGR)

Example:
P:3:32:32:1736559000000:1736560123000:0,0,4294967295,...

Notes:
- Pixel data is a raw dump by design
- No compression or encoding is applied

----------------------------------------
3.2 PLACEMENTS SECTION
----------------------------------------
Begins with:
PLACEMENTS

Defines where sprites are placed on the sheet grid.

L-RECORD FORMAT:
L:<spriteId>:<xCell>:<yCell>

Field Definitions:
- spriteId  ID of sprite defined in SPRITES
- xCell     Grid column index
- yCell     Grid row index

Example:
L:3:5:2

----------------------------------------
3.3 META SECTION (PER-SPRITE METADATA)
----------------------------------------
Begins with:
META

Defines optional metadata for individual sprites.
This data powers the Metadata dialog in the editor.

M-RECORD FORMAT:
M:<spriteId>:<name>:<notes>

Field Definitions:
- spriteId  ID of sprite this metadata applies to
- name      Human-readable sprite name (string)
- notes     Optional freeform notes (string)

Example:
M:3:PlayerIdle:"Main idle animation frame"

Notes:
- Strings may be empty
- Colons inside strings should be avoided or escaped
- Absence of an M-record means default/empty metadata

----------------------------------------
DERIVED DATA (NOT STORED)
----------------------------------------
The following values are calculated at load time:
- wCells
- hCells

Derived as:
wCells = ceil(wPx / gridCellSize)
hCells = ceil(hPx / gridCellSize)

----------------------------------------
IN-MEMORY SPRITE OBJECT (REFERENCE)
----------------------------------------
This is NOT file format, but the in-editor representation:

spriteIndividualTemplate:
- id
- name
- notes
- createdUtc
- modifiedUtc
- wPx
- hPx
- pixels (Uint32Array)
- xCell
- yCell

----------------------------------------
DESIGN PRINCIPLES
----------------------------------------
- File metadata describes the container
- Sprite metadata lives in META, not JSON
- Pixel data remains a raw dump
- JSON used only where structure is beneficial
- Format must remain inspectable and editable by hand
- Forward-compatible by design
